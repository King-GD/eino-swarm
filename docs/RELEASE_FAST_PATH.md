# 发布执行最短路径与已知阻塞

本页是 [RELEASE.md](RELEASE.md) 的执行摘要，沿用 `F-430` / `C-010`，不新增发布入口、
放宽门槛或承诺全流程几分钟完成。原生操作仍按[原生测试最短路径](NATIVE_TESTING_FAST_PATH.md)。

## 开发验证完成，再交接发布

1. **先排廉价阻塞。** 确认目标仓库、已授权平台、干净的独立候选、版本分配、锁文件依赖、
   签名与原生通道。保留用户原工作区；发布候选缺依赖时先按锁文件准备，不能等到占用 guest 才安装。
   `make release-check VERSION=x.y.z` 检查来源、签名和远端条件；它可能联系远端并取得本地锁，
   不是纯离线检查，也不执行完整测试。
2. **在开发验证阶段修产品和测试工具。** 按 AGENTS 运行受影响的强制检查；完整 Mac 候选沿用
   `make release-verify VERSION=x.y.z EVIDENCE=/absolute/private/run VERIFY_JOBS=2`。
   它要求干净的独立 Git checkout，不能直接拿 linked worktree 运行。先核对专项驱动器的
   输入、鉴权、请求格式与预期页面，再运行昂贵的原生场景。测试服务和驱动器的矛盾必须先修正。
3. **冻结后交接。** 固定完整 SHA、版本、已通过检查的原始回执、最终签名包和 SHA-256、
   原生接受及完整清理结果；必要的形式化验收与审查仍按已启用的规则完成。发布阶段复用这些
   有效结果与原包，不因换执行者而重新跑同一套检查或重建同一版本。
4. **执行已授权发布。** 使用现有 `make release VERSION=x.y.z`；它选择本批仍待交付的平台。
   普通 release 不自动执行 headless 或原生验收。先检查下文工具缺口，不能假定所有平台都已
   实现“验收后原包上传”。发布后核真实 tag、各必需附件的完整下载哈希、更新入口及 TestFlight 状态。

复用 headless 结果须使用**同一命令、同一 evidence 目录**，由现有 StageRunner 判断身份、
工具链、依赖、配置及输入输出是否仍匹配；不要手改回执为 passed。不同目录里临时跑出的结果
不会自动导入。代码、包或测试驱动器变化时，检查其影响并重新取得相应证据；变更 Go 仍遵守
全仓 race 门槛。原生接受不能自动继承到变化后的字节。

并发遵守现有宿主租约，最多两个独立重阶段；同一 guest 串行到清理结束。不要在统一验证旁边
另启相同范围的 `make check`、Go race 或 E2E。原始失败、取消及清理错误必须保留，新的通过
不能反推原失败已经查明。证据整理、交接和审查也计入墙钟，不另造多层私人控制器充当正式入口。

## 耗时与失败报告

按以下阶段记录开始、结束、执行与排队时间；并行阶段不能简单相加：

| 阶段 | 完成含义 | 耗时边界 |
| --- | --- | --- |
| 开发验证与工具准备 | 必需测试、驱动器、签名及通道可用 | 按实际检查预算，不能包装成打包耗时 |
| 冻结候选构建 | 最终包、签名、版本与来源一致 | 以几分钟为优化目标，缓存和环境必须注明 |
| 原生接受 | 对应场景通过，进程与数据清理确认 | 普通 Mac smoke 整轮 60 秒；专项另计 |
| 分发 | 原包上传成功，公开下载字节匹配 | 与构建分别计时；已完成平台保留结果 |
| Apple 处理与审核 | VALID、内外测可用及组关联齐全 | 外部等待单独报告，不承诺几分钟审批 |

超出已声明预算、遇到工具故障或外部等待时，立即报告准确阶段、已完成平台、原失败与下一步。
先提出能区分原因的最小检查；不要不断添加脚本、重跑或扩展审查来隐藏阻塞。原生故障仍须完成
清理，不能用预算耗尽作为遗留进程的理由。共享账本通过现有 `release.lock` 串行修改，不能
同时启动第二个发布者来抢过等待。

历史测量：v0.1.81 最终桌面多架构和 iOS 签名构建控制器用时 **175.79 秒**；这是该轮构建
范围，不包含 Android、全量测试、通道准备或排障，也不是新的 SLA。首次发布程序因 Apple
读取超时以非零结束；当时已确认上传，后续按当前状态补齐缺失组与审核，没有重传 IPA。
GitHub 首次公开为 **2026-11-17 07:45:02 +08:00**，iOS 严格可用首次观察为
**08:02:53 +08:00**；独立远端验真在 **08:04:14 +08:00** 完成。构建、公开、可用与验真是不同时间。

## v0.1.81 暴露的专项陷阱

| 现象 | 已知证据与下一次操作 |
| --- | --- |
| Windows 选 Tab 后立即读到未选中 | 该轮受控观察中，一次 Select 后约 227ms 新鲜读取已选中；即时 false 不足以判定最终失败。驱动器应一次输入，在原有单调期限内重取同一窗口/PID/Tab 身份并确认选中，保留身份与业务断言；不要重复点击或删除 guard。该修正当时在私有 QA 驱动器中，不代表仓库已有通用 Windows runner。 |
| 试听后 generic voice 错误 | Windows 驱动器配置了 personal/custom，正确请求 `stream_format: audio`，而当时的测试服务强制 `sse`。发布前对真实路由核请求契约；账号源的 PCM 请求用 `sse`，personal/custom 用 `audio`。请求协商与响应采用 raw PCM 或 SSE 是两件事。私有 fixture 的兼容修正不能被称为生产客户端修复或账号登录验收。 |
| Android 浏览器未到授权页 | 首次 miss 缺少浏览器点击的完整证据，原因仍 unknown。后续加单次输入前后观察才获得新成功轮；保留原失败，不能把一次新通过说成已修复浏览器或网络。 |
| 私有 Go overlay 加覆盖率后仍表现为旧实现 | 该轮 `-overlay` 配合 `-cover` 的定向测试与无覆盖率、相同断言的 race 测试行为不同；只记录已观察的差异，未确诊工具链根因。核实际编译输入并保留两份日志；最终产品门槛使用真实候选，不拿诊断 overlay 代替。 |
| Windows 账号凭据被拒绝 | 沿真实文件核 owner/DACL 和具体 I/O 错误；不能放松凭据保护来通过发布。产品修复意味着候选变化，需重绑受影响验证。 |

原生 helper、fixture 或观察器变化时，记录源码差异、派生二进制、驱动器与实际包的各自哈希。
`go version -m` 中的干净 VCS 可能只证明 overlay 的基础源码，不能证明派生 fixture 是未经修改的构建。
这些历史事实用于选择排障方向，不接受下一候选，也不要求为每次发布重新构造全部诊断。

## Apple 处理与审核恢复

上传确认、VALID、提交审核与外部可用分别报告。读取超时先查当前构建/上传状态，不重新上传；
已存在 review 时先读其状态，不重新提交。私有配置、凭据、具体 group/build ID 和原始证据留在
受控私有目录，不复制进仓库。

使用现有配置指向的 App Store Connect 客户端做 GET-only 观察，按实际 `links.next` 读完需要的
集合；本页不是新增的 CLI：

- `apps/{app}/builds?limit=200`、`apps/{app}/buildUploads?limit=200`：本地筛选本批版本号。
  该轮 app-scoped builds 的 `filter[version]` 被 Apple 明确拒绝，不能无变化重试该 400。
- `builds/{build}/preReleaseVersion`、`buildBetaDetail`、`betaAppReviewSubmission`：分别核 marketing
  version、内外部状态和实际 review。成功响应 `data: null` 与请求错误必须区分。
- `apps/{app}/betaGroups?limit=200`、`betaGroups/{group}/builds?limit=200`，以及
  `betaGroups?filter[builds]={build}&limit=200`：核所有配置组的正反关联。
  不调用不受支持的 `builds/{build}/betaGroups`，也不叠加第二个 relationship filter。

需要改变状态时，先核来源/IPA 与本批身份、获得现有发布锁，再通过现有客户端只补确实缺失的
合规声明、组关联或审核提交；保留请求前后证据。任何写请求确认未知，先 GET 澄清，不能直接
重发。成功标准保持：VALID、未过期、内部 `READY_FOR_BETA_TESTING`、外部 `IN_BETA_TESTING`、
存在的 review 为 `APPROVED`，所有配置组正反关联一致。之后才按现有记录流程保存成功与完成交付。

## 已补齐的发布工具路径

- Windows 批次的 `release_windows_validation` 绑定通过状态、版本、源码和两个架构的
  `status`、`arch`、`asset_name`、`asset_sha256`。统一入口直接校验并上传保留 ZIP，不调用
  `make windows-release`；缺失、冲突、改字节或 PE 架构不符均拒绝上传。部分已公开时，先核
  已有附件的远端 digest，只允许另一架构的精确已验收原包补传。无验收回执的旧构建路径保持，
  原生准入门槛仍生效；部分公开不能回到重建路径。
- 默认发布顺序为 Mac → Android → Windows → Linux → iOS（仅包含本批必需且未完成的平台）。
  非 iOS 平台逐一持久化结果后才进入 Apple 阶段，因此 Apple 处理／审核等待不阻塞这些上传；
  发布仍串行持锁，不同时开多个发布者。任何必需平台未完成，整体仍返回非零。
- iOS 复用本应用账本中已确认发布的历史构建，不再逐个请求它们的详情或 review，也不改写
  首次可用日期。未知、待交付候选仍查询和阻断；普通日发布限制保持。发布恢复使用原入口。
- 当前构建的正式只读入口如下；它执行 GET、完整组分页和双向核对，不运行 quota、Xcode、
  archive、upload、合规写入、组关联或审核提交，不写发布状态或交付账本，也不创建发布锁。
  已保留的首次公开证明不能替代这次实时观察。

```bash
python3 -B tools/release.py --version x.y.z --platform ios --ios-status \
  --source-dir /absolute/frozen-checkout
```

`--source-dir` 的 HEAD 必须匹配该版本已保留的源码身份。输出 JSON 的 `status: available`
仅在严格内外测状态、未过期、营销版本与所有组的正反关联通过时返回，exit0；等待／失败状态
exit1，参数组合非法 exit2。这个只读入口不能与 `--check`、`--verify`、发布授权原因或其他平台
组合。它不记录交付成功；需要变更或正式落证时仍使用持锁的 iOS 发布恢复流程。

回归入口：`python3 -B -m unittest discover -s tools -p 'test_release*.py'`。这些实现消除已知的
重建和重复远端查询，不意味着全量验证、网络或 Apple 审批已有几分钟的保证。
